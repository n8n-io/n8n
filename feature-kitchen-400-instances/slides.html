The 400 instances dilemma

How do you move a workflow from a safe place to production — without duplicating it, losing data, or shipping empty credentials?

~40 people · 50 minutes · we need your setups, not your applause

Cold open · a true story

It worked in dev.

Friday. A builder copies an invoice workflow into production by hand. The canvas is identical. The credential has the same name. Monday, finance asks why 1,200 invoices went nowhere.

Nothing errored

The workflow ran. It just ran against the wrong account.

Nobody reviewed it

There was no diff to review. There was a copy.

No way back

The dev version had already moved on.

House rule: interrupt. If a model in here would fail in your org, say it in the room.

Why so many instances?

400

is not a joke. it is a topology.

Stages

dev / test / staging / prod. isolation first, then promotion.

Blast radius

a bad workflow must not touch live money, PII, or customers.

Tenants & regions

one template, many copies: country, brand, business unit.

Trust boundaries

prod is locked. credentials never leave. networks do not talk.

Hands: 1 instance · 2–5 · 6–20 · 20+ · “don’t ask”

What they tell us

Manual promotion fails in three boring ways

duplicates

Two workflows, one name

Copy-paste between instances. IDs drift. Nobody knows which one is true.

data loss

Overwrite vs skip

Full import stomps prod edits. Partial copy leaves nodes, folders, and data tables behind.

credentials

It looks ready

The graph arrives. The secrets do not. First prod execution is the test.

The bar is not “it copied.” The bar is I trust this will work in production.

What people do today

Two workarounds. both are load-bearing.

source control

Git as the pipe

Each instance is an environment. Push from dev, pull on prod. Workflows, projects, folders, tags, variables, data tables, credential stubs — not secrets.

instance import

Move the whole world

Export / import an instance (or a pile of workflows) when you bootstrap, migrate, or recover. Poor as a daily promote button.

Git is already the closest thing we have to a promotion API. The UX is still “you are a Git operator.”

What we explored

Four promotion models

fits many orgs

1. Git is the source of truth

Instances never talk. GitHub / GitLab / Bitbucket (or any Git remote) holds the artifacts. Review, audit, rollback come for free.

new UX on 1

2. Instance → instance through a provider

You click Promote. n8n still writes Git under the hood. The provider is the trust and audit layer.

dropped for now

3. Instance → instance direct

Prod opens a hole for another n8n. Auth, network, confused deputy, “who can push live graphs?”

maybe later

4. Environments inside one instance

One URL, many stages. Elegant for small teams. Painful migration, shared blast radius, credential isolation is the whole product.

Row 3 is the uncomfortable one. The model we dropped is the only one that fits it. Tell us if you are row 3.

The direction

Promote in n8n. Persist in Git.

You stay in n8n

Pick workflows (and friends). Choose the target environment. See a diff. Confirm.

Git still exists

Branch, PR, history, CODEOWNERS, your existing controls. We do not replace your platform team.

Secrets stay put

Credential shape and IDs can travel. Values do not. Variables and external secrets fill the gap per instance.

If Git is banned in your prod network, say so later. That constraint kills this model.

Why not the other two

Direct sync and “envs in one box”

Direct instance talk

  • Prod must accept writes from another server
  • Identity: user? instance? CI job?
  • No natural review surface
  • One stolen token promotes everything

Environments in one instance

  • Customers already split instances for a reason
  • Hard to migrate 400 boxes into one mental model
  • Isolation (data, credentials, RBAC) becomes our problem overnight
  • Still useful later for simpler teams

Kitchen problem 01 · credentials

The workflow that looks ready

Dev Slack OAuth ≠ prod Slack workspace. Git syncs name, type, and id. Secrets stay on each instance. The canvas is identical. The first prod run posts to nowhere — or fails.

A. Block promote

Refuse until every credential on the target is mapped and tested.

B. Promote anyway

Ship the graph. Mark missing secrets. Let ops fill them in.

C. Copy secrets

Never, sometimes, only with a vault, only same org?

2 minutes, tables: what would you trust on a payroll workflow?

Kitchen problem 02 · diff

What did we actually change?

A workflow file is a large JSON graph. Git will say 400 lines changed. The builder changed one HTTP URL and dragged a node.

Text diff

Honest, noisy, scares reviewers, misses “this node moved 8px.”

Node-aware diff

Added / removed / param changed. We must define equality. Positions? notes? pin data?

Behavioral diff

Same graph, different outcome: credentials, variables, data tables, pinned data.

Vote: I need to approve a picture · a param list · a test run on prod-like data

Kitchen problem 03 · merge & fleet

Two builders. 400 copies.

Conflict

A and B both edit the same node on different branches. JSON merge is roulette. Last-write-wins silently drops work. A lock freezes the team.

Fleet

One global template, 400 regional instances, local forks for tax rules. Promote-all stamps over forks — or drift lives forever.

Pick one pain to solve first: two-person merge · branch-per-env · template vs 400 forks
