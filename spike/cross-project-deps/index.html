What can a workflow depend on in another project?

The rules below mirror the checks in subworkflow-policy-checker.ts, workflow-execution.service.ts (error workflows), credentials-permission-checker.ts, the data table proxy and resolve-variables.ts. Agents, apps and external secrets are out of scope. Follow the tour, or pick a mode and change the inputs. The animation replays on every change.

Decision trace

Callee decides

Sub-workflows and error workflows. The called workflow's caller policy decides. Only home projects are compared, and sharing is ignored.

  • Default workflowsFromSameOwner blocks every cross-project call.
  • Personal projects follow the same rule in every direction.
  • The dependency is a visible ID in the caller (node parameter or settings.errorWorkflow). callerIds adds a reverse reference.
  • To set an error workflow, the author must be able to read it. It must also be published, with an enabled Error Trigger.

Caller decides+ who runs it

Credentials. n8n checks the routes in this order:

  • The personal project of an Owner, Admin or a custom role with instance-wide credential:use can use every credential.
  • Project route: the home project owns the credential or has it shared, or the credential is global. A personal workflow shared with another personal project also reaches that project’s credentials at run time.
  • Acting-user route: the publisher's (or session user's) own access. Instance-wide credential:use does not count in a team project.

Never crosses

Data tables and variables stay in the workflow's home project.

  • Data table nodes look up tables in the home project only. Workflow sharing and team membership do not help.
  • $vars holds global variables plus the home project's variables. A project variable overrides a global one with the same key. A missing key is undefined, and no error is raised.
