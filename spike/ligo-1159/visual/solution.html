What the rule means

A dependency is a sub-workflow, an error workflow or a credential that a workflow needs. A reference that will not resolve after the operation is a gap. Each gap gets the best exit that the user can take.

Gap: a static reference from an item of the operation to a resource that will not resolve after the operation.
Strict environment: "allow incomplete" is off. A gap stops the operation. This is the default.
Incomplete operation: a Promote or Apply that writes items with gaps, after the user confirms the list. Opt-in for each environment.
Placeholder: an empty credential with a marker. An incomplete Apply creates it in a project that uses it, when the destination does not hold the credential. It moves to its owner when the real credential arrives.
Works on the source: the target exists, is not archived, and the item can use it. When the check cannot tell, the reference counts as working.
Changes view: the changes grouped by project. A selection can span the projects that the user can access.
Cast used on this page: Sales (P) owns the workflows, Platform (Q) owns the credential, Ops (R) owns the sub-workflow. Alice has a personal project.

Chosen model against the alternatives

Two models came before this one: the previous revision, "dependencies first" with hard blocks and no "apply anyway", and "Promote informs, Apply decides", where Promote never fails and Apply resolves each gap with a home that the user selects.

What changed from the previous revision

  • A gap has exits: "Include it" for a user with the right, "Ask the owner" for a user without it.
  • "Allow incomplete" is an opt-in setting of each environment. Strict stays the default.
  • A selection can span projects. Cycles across projects no longer need an instance Promote.
  • The owner of a credential on the destination follows the branch. A placeholder from an incomplete Apply moves to its owner.

What the chosen model takes from the alternative

  • An operation can finish with gaps. Here only when an admin opts in, and the home of a credential still comes from the branch.

Why the alternative is still not chosen

  • The destination differs from the source. A credential lands in a home that the user selected, and the source never sees it.
  • It needs a format addition (the owner hint) to name a home that the branch path already names.

Cost of the chosen model

  • On a strict environment, a user without access waits for the owner team. "Ask the owner" makes the wait visible.
  • New surfaces: the changes view across projects, the report, the inbox request, and the setting.

Open decisions for a human

Each scenario that depends on one of these decisions carries its number. The scenarios show the recommended answer. Decisions 5 to 8 come from the specification review. Central credentials (IAM, Q1) and one repository for each project (LIGO-1399) are decided elsewhere.

Rejected options and what is not settled

For the review: what the solution says no to, and what it leaves open.

Rejected options
Where solution.md and the specification disagree

Flag: repositories for each project (separate spike)

Self-contained by default. LIGO-1399 decides the details. Problems to solve:

  • A credential of another project. A copy in each repository duplicates secrets.
  • A sub-workflow of another project lives in another repository.
  • Workflows that call each other across two repositories.
  • Instance resources belong to no project.

"Allow incomplete" gives that spike its "reference only" option.

What the code does not settle

  • The publish paths for a workflow whose credential is a placeholder (decision 2).
  • A static reference in a disabled node. The check treats it as a reference. Not verified against the requirement exporter.
  • The cost of the branch inventory check on a large branch. Not measured.

Known limits

  • References made by expressions are not checked. An expression needs an execution context. This is permanent.
  • An older destination applies the branch as today. It has no Apply gate: a gap arrives as a broken reference.
  • A move into a personal project stops the Promote in both modes, also every instance Promote.
  • A move out of a project that the package does not hold needs an instance Apply.
  • After the upgrade, each workflow that uses a top-level credential has a gap at its next Promote.
  • A review across projects holds the open-review gate of each of its projects. Who can see it is not decided (LIGO-1006).
  • A global credential that a personal project owns is a personal dependency for each workflow that uses it.
  • The result of a check shows that an id exists, also for a target that the user cannot access.
  • A workflow that an instance Apply keeps is not checked further.
  • Not covered by scenarios: agents, instance to instance, the life cycle of a request to the owner, and the API and CLI shape of a confirmation.
