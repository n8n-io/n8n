What the rule means

A dependency is a sub-workflow, an error workflow or a credential that a workflow needs.

Scope: the projects that an operation writes. Instance Promote and Apply: all team projects. Project or selective: a selection inside one team project.
Content: workflows, folders, and the resources that a project in the scope owns.
Closed branch: a branch that obeys the rule. Each dependency of its content is also content of the branch.
Cast used on this page: Sales (P) owns the workflows, Platform (Q) owns the credential, Ops (R) owns the sub-workflow. Alice has a personal project.

Chosen model against the alternative

The alternative is "Promote informs, Apply decides": Promote never fails on a dependency, and Apply resolves each gap on the destination with a home that the user selects, a grant, or "apply anyway".

Why the alternative is not chosen

  • The destination differs from the source. A credential lands in a home that the user selected, and the source never sees it. A diff between source and destination then needs rules for each kind of difference.
  • A reference to a personal workflow can never be satisfied, so the Apply block returns on each Apply.
  • It needs a format addition (the owner hint) to make proposals that a closed branch gets from the path.

What the alternative does better

  • No Promote friction and no coordination between teams.
  • Repositories for each project need no extra rule: every external reference is a requirement.

Cost of the chosen model

  • A team waits for the owner team of a dependency.
  • Promotes that pass today start to stop. This is why the block is a warning for one release first.

Rejected options and what is not settled

For the review: what the solution says no to, and what it leaves open.

Rejected options (12)

Flag: repositories for each project (separate spike)

"Promote the dependency first" then means a Promote to another repository. Problems to solve:

  • A credential of another project. A copy in each repository duplicates secrets.
  • A sub-workflow of another project lives in another repository.
  • Workflows that call each other across two repositories: neither can go first.
  • The check that a dependency was promoted reads another connection, or trusts a record.
  • Instance resources belong to no project.

Directions: self-contained projects, declared external dependencies ("sidecar"), or a mix. This model must not exclude any of them.

What the code does not settle

  • A credential transfer on the source from Q to Q2. The package can then hold one credential id under two project folders. The reader behavior for a duplicate id is not verified.
  • A static reference in a disabled node. The check treats it as a reference. Not verified against the requirement exporter.
  • The cost of the branch inventory check on a large branch. Not measured.

Older destinations and rollout

  • No format change, so an older destination applies a closed branch as today. It has no Apply gate.
  • The Promote check warns for one release, then blocks (decision 5).
  • The Apply side of a move ships at least one release before the Promote side.
