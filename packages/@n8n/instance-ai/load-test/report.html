What a concurrent workflow-builder costs in memory

A load-test harness drives N distinct users through real multi-turn workflow builds against the live model, so the backend's per-user state actually multiplies. These are measurements from a dedicated cloud instance — not projections.

A 640 MB instance cannot run 10 concurrent builders. It OOM-crashed the pod on two of two attempts, ~32–45 s in, before any workflow had been created. The arithmetic: 495 MB idle leaves ~145 MB for a load that wants ~245 MB. Doubling the limit to 1280 MB made the identical workload pass three times over.

What we learned

  • 01
    Idle cost dominates on small plans. ~495 MB is gone before anyone arrives, so small instances are constrained by the baseline, not by per-user cost. That is why 640 MB died at 10 users and why doubling the limit fixed it so decisively.
  • 02
    No memory leak. After a full lifecycle — conversation, thread deleted, forced GC — retained memory is ~0.4 MB per user, reproduced in every run at every concurrency level. Peaks fall back to the 495 MB baseline afterwards.
  • 03
    The cost is concurrent run start-up, not accumulated state. Both OOMs died in turn 1, before any workflow existed. Prompts, tool registries, sandbox handles and model streams — that is where to look to reduce the footprint.
  • 04
    Conversation length adds peak, not retention. Doubling turns raises the transient peak but nothing accumulates.
  • 05
    Latency degrades before memory does. Median build time held roughly flat across concurrency while the tail stretched from ~60 s at one user to ~200 s at thirty. If anything limits concurrency today, it is latency rather than RAM.

Read these before quoting the numbers

  • Peaks above N=20 are lower bounds. The harness hits 409 "run already active" on follow-up turns under high concurrency. At N=30, 20 of 30 users delivered 3 turns instead of 4 — roughly 17% less work than the label implies. Needs fixing before trusting numbers above 20.
  • Memory was read from Grafana, not sampled by the tool. Cloud /metrics is firewalled, so the harness recorded phase boundaries and the peaks were read off the dashboard.
  • Marginal cost is approximate, not precise. A three-point least-squares fit did not reproduce across runs; the ~14 MB figure comes from endpoint estimates, which did.
  • Not tested: sustained/continuous load (every run was burst-then-idle), Postgres, multi-main, and anything above 30 concurrent builders.
