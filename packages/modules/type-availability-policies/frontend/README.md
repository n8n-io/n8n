# @n8n/frontend-module-type-availability-policies

Frontend module for node type availability policies. The editor-ui shell consumes it from
source through `src/app/modules.manifest.ts`, so there is no build step and no `dist`.

The descriptor `id` must match the backend module id
(`packages/cli/src/modules/type-availability-policies`). Both `settings.activeModules` and
`/rest/module-settings` are keyed by that string, and a mismatch fails silently.

The module is license-gated on `feat:typeAvailabilityPolicies` and is not a default module. Enable it
in a dev instance with `N8N_ENABLED_MODULES=type-availability-policies`.

`useTypeAvailabilityPoliciesStore` answers whether a project may use a node type or a credential
type. The store is passive: it does not watch the route, because the projects store lives in the
shell. It keeps one answer for each project it loaded, from
`/projects/:projectId/available-types` and `/projects/:projectId/available-credential-types`.
`fetchForProject(projectId)` loads a project and makes it the active project. A lookup without a
project answers for the active project. A switch back to a loaded project keeps the old answer
until the refresh arrives. The shell calls `reload()` after a community node install, because the
server answers only for the node types it has loaded. When the module is off, a request fails, or
the project has not loaded yet, every lookup reports "available". The backend checks are the real
gate, so the frontend never blocks on a missing answer.

A surface that lists, adds or configures node or credential types starts with
`useTypeAvailability(projectId)`. It loads the project and returns `nodeTypeRestriction(type)` and
`credentialTypeRestriction(type)`, which answer for that project even when another surface made a
different project active. Do not call `fetchForProject` from a component.

A credential-only node (`n8n-creds-base.<credentialType>`, generated by the editor from a
credential type with `httpRequestNode`) is restricted when HTTP Request is restricted under the
node kind, or when the credential type it wraps is restricted under the credential kind.
`getNodeTypeRestriction` composes that, so blocking `virusTotalApi` hides the VirusTotal node
and leaves HTTP Request and the other credential-only nodes alone. The backend never sees the
generated name and refuses a node type rule on it; the credential type rule is the one to write.

```bash
pnpm turbo typecheck lint test --filter=@n8n/frontend-module-type-availability-policies
```

Use turbo and not `pnpm --filter`: this package reads its platform dependencies from source,
and on a cold tree turbo builds them first.

`useNodeTypeRestriction(type)` turns the store answer into `isRestricted` and `restrictionScope`
for one node type. `isNodeTypeRestricted(type)` is the plain predicate for a list of nodes. Both
answer for the active project. The shell reads restriction through these or through
`useTypeAvailability`, and never through the store directly.

Pick the UX by what the surface does with the type:

| Surface                                  | Pattern                                                                 |
| ---------------------------------------- | ----------------------------------------------------------------------- |
| A picker or a list of types              | Sort restricted rows last and show `RestrictedNodePopover` on them      |
| A node or tool that is already placed    | The canvas lock badge, `RestrictedNodePanel` or `RestrictedToolCallout` |
| A flow that closes before it can explain | The shell's `useRestrictedNodeWarning` toast                            |

Tests stub the store through `mockRestrictedNodeTypes` and `mockRestrictedCredentialTypes` from the module's `__tests__/mocks`.

`ContactAdminModal` lists the admins who can lift the restriction, with a mail link: the project
admins when a project admin can lift it, otherwise the instance owners. The surfaces below render it
as a sibling of their own content, so a popover that closes never unmounts the open dialog.
`RestrictedNodePopover` is the explanation for a row in a list: the lock trigger, the hover-opened
popover and the dialog. The caller passes the row element and whether the row is keyboard-active.
`RestrictedNodePanel` is the builder-facing explanation of a blocked node in the NDV, with the
contact and replace actions. The shell renders the popover and the panel where a restricted node
appears; the module owns their copy and behaviour.

`useSubWorkflowRestriction({ parentWorkflowId, node, enabled })` tells whether the sub-workflow
an Execute Workflow node calls uses a blocked node type. It reads
`/workflows/:workflowId/sub-workflows/:subWorkflowId/policy-check`, which judges the
sub-workflow against its own project. The store caches one answer for each parent and
sub-workflow pair, and callers that render the same call share one request. A 404 or 403 is
cached as a refused call. Any other failure stays out of the cache, so the next fetch retries
it, and `checkFailed` reports it. Only a stored
sub-workflow selected by id is checked: inline and URL sources, and expressions, are skipped.
`RestrictedSubWorkflowCallout` is the NDV explanation. It refetches on open, offers a retry
when the check failed, and names the
sub-workflow's project only when the server returned its name. The shell passes `enabled`, which
must require `workflow:update` on the parent, because the endpoint refuses other users.

`getPolicyViolations(error)` reads the structured violations off a refused save, publish or run,
and `PolicyViolationList` groups them by scope and lists each blocked node or credential type,
with an optional jump. The shell resolves display names and the nodes to jump to, because only
it holds the open workflow.

`packages/@n8n/module-cli/frontend-module-guide.md` holds the descriptor contract, the
registration points, the import boundaries and the setup a module needs to render UI.
