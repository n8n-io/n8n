What each layer gets and what the protocol could carry

External MCP clients

  • The build sandbox: open_workspace, file and shell tools, build_workflow (tsx, multi-file, lint) — also one-call with files
  • The edit loop: get_workflow_as_code → edit → rebuild with workflowId
  • Confirmations before writes on form-capable clients (archive, publish, unpublish, restore, update)
  • Tool groups and approval details in _meta; ignorable by any client

The Assistant

  • 14 native tools and the workspace tool set replaced by the server's: discovery, reads, lifecycle, build, sandbox
  • Same UX: approval cards, “Always allow” grants, admin rules and Auto-mode judge all still apply — client side
  • Durable HITL over the protocol: the suspension keeps the signed requestState; resume retries the call, survives a restart
  • Workspace bound to the thread; workflow tab and thread ownership restored by the bridge

Shortcuts, drawbacks, and the road to production

Shortcuts taken

  • In-process transport: handler.fetch(), no token, no middleware — the auth story (M5) is untested
  • No flag: native tools replaced wholesale; the workflow-builder skill switched off rather than rewritten
  • Container.get inside tools, handler-side HMAC instead of the SDK's requestState.verify, request() to dodge a client output-validation quirk
  • Verified by integration tests and manual runs — no LangSmith evals against the native Assistant

Drawbacks observed

  • Lost thread state: build→verify→debug loop, setup diffs, unverified-publish disclosure don't exist over MCP
  • Guidance drift: the skill's references (credential choices, model selection, trigger shapes) never reach the model; one run hit a name collision and self-recovered
  • No namespaces: collisions resolved by swap rules; workspaceKey on every call because the protocol has no session
  • Behaviour changes for everyone: confirmations on by default; Assistant builds counted as MCP builds; a JSON-RPC hop and a fresh server per call

Missing for production

  • Evidence: eval parity (native vs MCP Assistant vs Claude-over-MCP), latency and token budgets
  • Contract: tool naming/versioning, schema-parity tests in CI, first-party caller on the token for loopback/sidecar
  • Platform: a v2 MCP connection in @n8n/agents (promote the bridge), sandbox quotas/TTL for external callers, legacy tool names for persisted threads, i18n, telemetry attribution
  • Product: which Assistant behaviours become server tools (setup, verification) and which stay harness
Verdict: the protocol carries the tool layer; the harness, the policy and the session stay with the client — by design, not by accident.
